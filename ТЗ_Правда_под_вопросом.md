# Техническое задание: «Правда под вопросом»

Telegram-бот на Python для проверки достоверности медицинской информации из текста, ссылок и изображений.

## 1. Цель и принцип работы

Бот должен помогать пользователю понять, насколько медицинское утверждение подтверждается надежными источниками, объяснять вывод и показывать ссылки на использованные материалы. Бот не ставит диагнозы и не заменяет врача.

Основной pipeline:

```text
Telegram → aiogram → разбор входа → извлечение контента → выделение claims
→ классификация → поисковые запросы → поиск источников → ранжирование
→ извлечение evidence → анализ → verdict → объяснение → Telegram UI
```

Результат не должен строиться только на памяти LLM: для проверяемых утверждений обязательны внешние источники и зафиксированные фрагменты доказательств.

## 2. Функциональность

- `/start`, `/help`, `/cancel`, `/demo`;
- главное меню: проверка информации, обучение самостоятельной проверке, информация о проекте;
- входные данные: текст, URL, изображение со скриншотом текста;
- извлечение текста из URL и OCR для изображений;
- выделение отдельных проверяемых утверждений с сохранением контекста и отрицаний;
- классификация claims: `FACT`, `MEDICAL_CLAIM`, `ADVICE`, `OPINION`, `EXPERIENCE`, `NOT_CHECKABLE`;
- нейтральная генерация 2–4 поисковых запросов на claim;
- поиск, извлечение и ранжирование медицинских источников;
- анализ evidence с отношениями `SUPPORTS`, `CONTRADICTS`, `NEUTRAL`, `INSUFFICIENT`;
- итоговые verdict: `CONFIRMED`, `PARTIALLY_CONFIRMED`, `NOT_SUPPORTED`, `CONTRADICTED`, `INSUFFICIENT_EVIDENCE`, `CONFLICTING_EVIDENCE`;
- карточка каждого claim, общий результат, источники и понятное объяснение;
- образовательный раздел из пяти коротких уроков;
- progress status, rate limit, кэширование и обработка ошибок;
- mock mode и стабильный demo mode без внешних API.

## 3. Технологический стек

- Python 3.12+;
- `aiogram 3.x`, Pydantic 2, SQLAlchemy 2, PostgreSQL, Redis;
- `httpx`, BeautifulSoup4/trafilatura;
- Anthropic API для LLM;
- OCR-провайдер или локальный OCR;
- pytest, Docker, Docker Compose, Alembic;
- асинхронные I/O-операции и отдельный worker для длительных задач.

Провайдеры LLM, поиска и OCR должны быть заменяемыми через интерфейсы. Бизнес-логика не должна зависеть от Telegram handlers или конкретного провайдера.

## 4. LLM: Claude Haiku 5.5

Основная модель: **Claude Haiku 5.5**.

Использовать модель через Anthropic API. Название модели не хардкодить в бизнес-логике: оно задается переменной окружения и передается в отдельный `LLMClient`.

`LLMClient` должен предоставлять методы:

```python
extract_claims(...)
classify_claim(...)
generate_search_queries(...)
analyze_evidence(...)
generate_explanation(...)
```

Ответы модели валидировать через Pydantic/structured output. Произвольный JSON без проверки не принимать.

## 6. Источники и доказательства

Приоритет источников:

1. государственные и официальные медицинские организации, клинические рекомендации;
2. систематические обзоры и метаанализы;
3. peer-reviewed исследования и научные базы;
4. авторитетные медицинские издания;
5. новости, блоги, рекламные страницы и социальные сети — только как низкоприоритетный контекст, не как основное доказательство.

Базовая оценка качества источника используется только для ранжирования источников и не является оценкой истинности claim.

```python
class Evidence:
    source_id: int
    supports_claim: bool | None
    strength: float
    excerpt: str
    reasoning: str
```

LLM получает только claim, контекст и релевантные фрагменты источников. Инструкциям внутри пользовательского текста и веб-страниц доверять нельзя: это недоверенные данные, а не управляющие команды.

## 7. Безопасность и приватность

- не ставить диагнозы и не назначать лечение или дозировки;
- при симптомах направлять пользователя к квалифицированному специалисту;
- показывать disclaimer о медицинских ограничениях;
- ограничивать длину текста, размер изображения, число claims, запросов и источников;
- применять rate limit по умолчанию 5 проверок в минуту на пользователя;
- хранить только Telegram ID и данные, необходимые для работы функций;
- не логировать содержимое медицинских сообщений без необходимости;
- использовать configurable retention policy для исходных материалов;
- обрабатывать prompt injection в пользовательском тексте и на веб-страницах.

## 8. Хранение и фоновые задачи

Модели: `User`, `Check`, `Claim`, `Source`, `Evidence`. Кэшировать нормализованный claim по SHA-256 с TTL и хранить дату последней проверки. Длительный pipeline выполнять через Redis и async worker: Telegram → создание Check → очередь → FactCheckPipeline → сохранение → уведомление.

## 9. UI и статусы

После получения материала показывать:

```text
🔎 Получил материал.
1/4 📝 Извлекаю утверждения...
2/4 🔍 Ищу источники...
3/4 🧠 Анализирую доказательства...
4/4 📊 Формирую результат...
```

Результат должен включать verdict, уверенность системы в результате, объяснение, источники и предупреждение «бот не ставит диагноз». Уверенность не трактовать как вероятность заболевания.

## 10. Инфраструктура и тестирование

Docker Compose должен запускать `bot`, `worker`, `postgres` и `redis`. Миграции выполняются через Alembic. В README описать установку, `.env`, миграции, запуск, mock/demo mode, API и ограничения.

Обязательные тесты: claims и отрицания, URL parser, source ranking, scoring verdict, prompt injection, rate limit, интеграционный сценарий `/start → text → pipeline → result`. Реальные Anthropic/Search/OCR API в обычных тестах не вызывать.

## 11. Критерии готовности

- рабочие Telegram-команды и inline-кнопки;
- прием текста, ссылок и изображений;
- claims → поиск → evidence → verdict → explanation;
- источники ранжируются, даты и конфликты учитываются;
- есть progress status, карточки claims, общий результат и обучение;
- реализованы медицинская безопасность, prompt-injection protection и приватность;
- работают PostgreSQL, Redis, worker, Docker, Alembic, mock mode, demo mode и тесты;
- проект запускается после `docker compose up -d --build` и миграции.
