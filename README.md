# «Правда под вопросом»

Модульный фундамент Telegram-бота для проверки достоверности медицинской информации.

## Текущий статус

Завершен базовый этап: Python 3.12+, aiogram 3.x с `/start`, `/help`, `/cancel`, `/demo` и главным меню, типизированные доменные schemas и Enum, порты LLM/Search/Extractor/OCR/FactCheck, SQLAlchemy 2, PostgreSQL, Alembic, Redis, Docker Compose, pytest, Ruff и mypy. Команда `/demo` работает автономно: показывает стабильный пример отчёта без обращения к внешним API, Redis или PostgreSQL. Команда `/cancel` отменяет активную проверку в статусе `QUEUED` или `PROCESSING`.

Полный fact-checking pipeline на этом этапе намеренно не реализован. Этап 2 принимает текст,
URL и изображения, нормализует их в `ExtractedContent`, ограничивает загрузки и защищает URL-fetcher
от очевидных SSRF-рисков. Для OCR используется заменяемый mock provider. Внешние API и реальные
ключи не нужны для тестов.

Этап 3 добавляет `ExtractedContent → ClaimExtractionService → list[Claim]`: Claude Haiku 5.5
подключается через OpenRouter Chat Completions и structured tool output, а ответы валидируются Pydantic.
Большие материалы разбиваются на chunks, результаты дедуплицируются, а confidence означает только
уверенность выделения и классификации, не истинность утверждения.

Этап 4 добавляет `Claim → SearchQuery → SearchProvider → Source`: запросы формируются через
LLM-provider, результаты нормализуются, классифицируются по расширяемым domain rules,
дедуплицируются по canonical URL и ранжируются по отдельным `quality_score` и
`relevance_score`. В качестве поискового провайдера используется Yandex Search API v2;
наиболее релевантные источники можно обогатить через существующий URL extractor.

Этап 5 добавляет `Source → Evidence → EvidenceAnalysis → Verdict`: содержимое источников
извлекается через SSRF-защищённый HTML extractor, большие тексты разбиваются на chunks,
evidence извлекается Claude Haiku 5.5 через structured output, а итоговый verdict учитывает
тип и quality score источника, не используя простое голосование.

Этап 6 сохраняет завершённые проверки в PostgreSQL: `Check → Claim → Source → Evidence →
EvidenceAnalysis → Verdict`. Результаты сохраняются одной транзакцией через отдельный
repository layer, а Telegram формирует подробный отчёт с verdict, доказательствами,
источниками и медицинским дисклеймером.

Stage 6.3 добавляет `/history`: пользователь видит только свои последние проверки,
перемещается по страницам по пять записей и открывает сохранённый полный отчёт без повторных
вызовов OpenRouter или Yandex Search. Доступ к отдельной проверке ограничен Telegram user ID
на уровне SQL-запроса.

Stage 6.4 приводит Telegram-интерфейс к единому русскоязычному flow: добавлены отдельные
кнопки проверки, истории и образовательного режима, компактный отчёт с шестью локальными
названиями verdict, качественными (не процентными) формулировками основания и кнопками
перехода к истории или новой проверке. Во время обработки редактируется одно статусное
сообщение, а содержимое отчёта и пользовательские данные не попадают в callback data.

Stage 6.5 разделяет итоговый verdict и качество основания: релевантные прямые доказательства
оцениваются независимо от косвенных или нерелевантных материалов, а надёжный конфликт получает
отдельный статус. Основной отчёт стал компактнее и не повторяет объяснение; подробные доказательства
и источники открываются отдельно, с русскими пояснениями прямоты, релевантности и доступности
содержимого. Предпросмотр ссылок в Telegram отключён глобально для всех сообщений бота.

Stage 6.6 добавляет scope claim (`GENERAL`, `NARROW`, `COMPOSITE`, `COMPARATIVE`), компоненты
составных утверждений и отдельный класс `BACKGROUND` для полезного, но не доказательного контекста.
Проверка контекстных ограничений не превращает данные о смежной теме в прямое доказательство:
качественная косвенная поддержка может дать только `PARTIALLY_CONFIRMED` с ограниченной
уверенностью, а фоновая или нерелевантная информация не меняет verdict.

Stage 6.7 добавляет полезный ограниченный вывод для широких утверждений: отдельно показывается,
что удалось установить, и что осталось неустановленным. Качественная косвенная поддержка не
становится прямой и не повышает verdict до `CONFIRMED`; при недостатке данных пользователь всё
равно получает объяснение границ применимости вывода. Недоступные источники не включаются в
доказательную базу и отображаются только как найденные, но не изученные.

Stage 5.1 отделяет доступность контента от наличия поискового результата: CAPTCHA, anti-bot,
metadata-only и пустые страницы не поступают в Evidence Extraction. Evidence получает
`directness`, `scope` и `usable`, а verdict не может стать категоричным только на indirect
evidence или при отсутствии usable evidence.

Stage 6.8 улучшает отдельный экран доказательств и источников: карточки разделяют качество
источника, его авторитетность и соответствие теме с силой конкретного фрагмента, показывают
статус доступности и URL без домыслов, группируют полезные материалы раньше фонового контекста
и поддерживают постраничный просмотр. Недоступные, CAPTCHA и metadata-only источники не
выдаются за доказательства; они отображаются отдельно как найденные, но не изученные.

## Stage 7 — Production Hardening

До Stage 7 Telegram handler выполнял подготовку материала и весь fact-checking pipeline
последовательно в polling-процессе. После Stage 7 handler создаёт `Check` со статусом `QUEUED`
и добавляет job в Redis Streams, а отдельный `worker` выполняет подготовку и pipeline.
Статусы проходят `QUEUED → PROCESSING → COMPLETED` или `FAILED`, прогресс редактируется в
одном Telegram-сообщении.

Добавлены Redis rate limiting, дедупликация активных job, retry для job и transient HTTP-ошибок
(`429`, `5xx`, timeout) с exponential backoff, версионированные cache keys с TTL, дедупликация
одинаковых документов через разные URL, безопасные структурированные логи и healthcheck
PostgreSQL/Redis.

Новые настройки: `RATE_LIMIT_WINDOW_SECONDS`, `QUEUE_STREAM`, `QUEUE_GROUP`, `QUEUE_BLOCK_MS`,
`JOB_MAX_RETRIES`, `JOB_DEDUPE_TTL`, `EXTERNAL_MAX_RETRIES` и `EXTERNAL_BACKOFF_SECONDS`.

## Stage 8 — Search Recall & Evidence Coverage

Поиск теперь использует bounded query expansion: исходный, нейтральный, counter,
authoritative и research variants. При ошибке LLM применяется deterministic fallback. Все
результаты собираются в общий candidate pool, нормализуются, дедуплицируются по URL и очевидному
документу, ранжируются по quality/relevance и выбираются с мягким domain diversity.

Если первый проход не дал прямого или достаточного покрытия, запускается только один
дополнительный bounded pass по counter/authoritative/research направлениям. Coverage считается
отдельно от истинности утверждения: учитываются direct/indirect/not-relevant/background,
scope mismatch, contradictions, composite components и независимые source IDs.

## Stage 9 — Medical Answer Engine & Report Rewrite

Добавлен слой понимания утверждения: вопросы нормализуются в проверяемые пропозиции без потери
контекста, а для claim сохраняется reasoning category (`FACTUAL`, `CAUSAL`, `SAFETY`,
`TRANSMISSION`, `TREATMENT`, `PREVENTION`, `NUTRITION`, `RISK`, `COMPOUND` и другие).
Нормализованная формулировка используется для поиска и извлечения evidence, исходный текст — в
пользовательском отчёте.

Перед VerdictService появляется evidence matrix с отдельными признаками прямоты, соответствия
области, качества источника, релевантности и независимой группы источника. Итоговый verdict
считается правилами, а `MedicalSafetyValidator` запрещает положительный категоричный вывод при
ошибке анализа, отсутствии usable evidence, scope mismatch или наличии только косвенной связи.

Главный Telegram-отчёт сокращён до исходной формулировки, verdict, короткого объяснения,
качественной надёжности и медицинского дисклеймера. Подробности по-прежнему открываются
отдельно. Добавлена миграция для reasoning category и флага ошибки анализа evidence.

Образовательный режим содержит пять коротких уроков: формулировка утверждения,
первоисточник, качество доказательств, контекст и различие корреляции с причинностью.
Уроки открываются из главного меню и листаются inline-кнопками.

## Архитектура

```text
Telegram / aiogram
        ↓
handlers и keyboards
        ↓
порты сервисов (LLM / Search / Extractor / OCR / FactCheck)
        ↓
domain schemas
        ↓
repositories / SQLAlchemy / PostgreSQL
        ↓
Redis для будущих cache, rate limit и очередей
```

Бизнес-логика не должна зависеть от Telegram SDK, конкретного LLM SDK или поискового провайдера.

## Установка

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
cp .env.example .env
```

Заполните `BOT_TOKEN`, `OPENROUTER_API_KEY`, `YANDEX_API_KEY` и `YANDEX_FOLDER_ID` в `.env`.
Если Telegram API доступен только через прокси, укажите его адрес в `TG_PROXY_URL`, например
`http://user:password@proxy.example.com:8080`. Пустое значение отключает прокси.
В production-конфигурации Compose использует `network_mode: host`, поэтому прокси Xray
на этом же Linux-сервере указывается как `socks5://127.0.0.1:10808`. PostgreSQL и Redis
для этой схемы также указываются через `127.0.0.1` на опубликованных локальных портах.
Для OpenRouter и загрузки веб-источников приложение использует `EXTERNAL_PROXY_URL`.
Если он пустой, используется значение `TG_PROXY_URL`. Для Yandex Search используется
отдельный `SEARCH_PROXY_URL`; пустое значение отправляет поисковый трафик напрямую.
Для Yandex Search API создайте API-ключ с областью `yc.search-api.execute` и укажите каталог
облака в `YANDEX_FOLDER_ID`. По умолчанию используется российский поиск (`SEARCH_TYPE_RU`),
умеренный семейный режим и XML-ответ.

Основная LLM-модель: Claude Haiku 5.5. Укажите точный идентификатор модели из OpenRouter
через `OPENROUTER_MODEL`, например `anthropic/<model-id>`.

## Docker Compose


## Безопасность

Секреты хранятся только в `.env`, который исключен из git. Пользовательский текст и содержимое веб-страниц являются недоверенными данными. Полные медицинские сообщения не должны попадать в логи. Бот проверяет информацию, но не ставит диагноз.
